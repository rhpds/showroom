= zerotouch_showroom

An Ansible role that deploys "zero-touch" flavored Showroom lab instruction environments to OpenShift clusters, with integrated terminals, VNC, cloud-provider credentials, IronRDP, and split setup/runtime automation containers.

== Overview

This role was ported from `redhat-cop/agnosticd`'s v1 `ocp4_workload_showroom` role (plus its `deploy-showroom-helm-zerotouch.yaml` task) into this collection. It targets the same use cases as the v1 role: demo/workshop clusters and RHPDS's shared/CNV sandbox clusters, with tight integration into the zero-touch automation stack (`nookbag`, `zerotouch-automation`).

This collection also ships a newer, generic `ocp4_workload_showroom` role. The two roles are siblings, not interchangeable:

[cols="1,1,1",options="header"]
|===
|          |`zerotouch_showroom` (this role) |`ocp4_workload_showroom`

|Origin |Ported from AgnosticD v1 |Rewritten from scratch for this collection
|Deployment types |`helm` and `argocd` |`helm` only
|Extra tabs |cloud-provider credentials, IronRDP, satellite, stacked/second terminal tab |NoVNC only
|Automation |split `setup_automation` / `runtime_automation` containers |single `runtime_automation` sidecar
|Default chart |`zerotouch` (see <<chart_selection>>) |`showroom-single-pod` (`2.x`)
|Auth model |dual: explicit `host`/`api_key` vars, or an optional kubeconfig file |explicit `host`/`api_key` vars only
|===

If you don't need the zerotouch-specific tabs/automation split, prefer `ocp4_workload_showroom` instead.

== What It Does

When `ACTION` is `create` or `provision`, the role:

1. Optionally builds a kubeconfig if deploying to a separate remote cluster (see <<auth>>).
2. Validates required inputs (`guid`, content Git repo).
3. Loads `user_data` (including optional per-user entries) via the `agnosticd.core.agnosticd_user_data` lookup plugin.
4. Looks up the cluster's apps domain (or uses `sandbox_openshift_apps_domain` directly on CNV sandboxes).
5. Creates one or more namespaces/projects (`showroom-<guid>` or `showroom-<guid>-<user>`).
6. Deploys via `helm` (default) or `argocd`, rendering the Showroom Helm chart with your content, terminal, and zero-touch automation configuration.
7. For `helm`, waits for the Showroom pod(s) to be running with all containers ready; on failure/timeout it collects a full pod describe plus container and init-container logs into the failure message.
8. Discovers the Showroom `Route` and writes `lab_ui_url` and `showroom_primary_view_url` into AgnosticD `user_info` (per user if multi-user).

When `ACTION` is `destroy` or `remove`, the role removes the ArgoCD `Application`/`ApplicationSet` (if that deployment type was used) and then deletes the namespace's `Project`.

== How It Works

- `tasks/main.yml` (do not modify) always runs `pre_workload.yml`, then dispatches to `workload.yml` + `post_workload.yml` (provision) or `remove_workload.yml` (destroy) based on `ACTION`.
- `tasks/pre_workload.yml`: if `showroom_openshift_api_url`, `showroom_openshift_api_token`, and `showroom_openshift_api_ca_cert` are all defined, writes a temporary kubeconfig file and sets `_showroom_kubeconfig` to its path. See <<auth>> — note these variable names do **not** have the `ocp4_workload_` prefix.
- `tasks/prepare-variables.yaml`:
* Asserts `guid` and `ocp4_workload_showroom_content_git_repo` are set.
* Optionally copies `agnosticd_passthrough_user_data` into each `userN` entry in `user_data` when `ocp4_workload_showroom_passthrough_user_data` is `true` (neither variable has a default; both are opt-in).
* Loads global + per-user `user_data` into `_showroom_user_data` via `lookup('agnosticd.core.agnosticd_user_data', '*')`.
* If `ocp4_workload_showroom_services` is set, logs the resolved URL for each entry (debug only; used by callers that also wire up additional tab services).
* Resolves `_deployer_domain` from the cluster's `Ingress` config, unless `ocp4_workload_showroom_use_sandbox_domain` is `true`, in which case `sandbox_openshift_apps_domain` is used directly (CNV sandboxes).
- `tasks/workload.yml`:
* Branches on `ocp4_workload_showroom_deployment_type` (`helm` or `argocd`).
* For each branch, detects single-user vs. multi-user from `_showroom_user_data.users` and loops accordingly, setting `_showroom_namespace` and `_showroom_vars` (user data merged with `showroom_vars` overrides) per iteration.
* `helm` deploys via `deploy-showroom-helm.yaml`; `argocd` installs the templated `application.yaml.j2` (single user) or `applicationset.yaml.j2` (multi-user).
* Always finishes by including `report-variables.yaml` once per namespace.
- `tasks/setup-namespace.yaml`: checks if the `Project` already exists; if not, tries a labeled (`guid`, `creator`) plain `Namespace` first, falling back to `ProjectRequest` (retrying and tolerating `AlreadyExists`, working around https://github.com/ansible-collections/kubernetes.core/issues/623[a kubernetes.core bug]) only if the `Namespace` attempt fails — matching the sibling `ocp4_workload_showroom` role's approach. This existence check is what allows this role to run safely on clusters/namespaces it doesn't exclusively own (e.g. CNV sandboxes). A genuine failure from both attempts (e.g. RBAC, quota) now fails the play instead of being silently swallowed. Optionally runs a self-provisioner smoke test (create + delete a test `ConfigMap`) when `ocp4_workload_showroom_test_self_provisioner` is `true`.
- `tasks/deploy-showroom-helm.yaml`: renders the Helm chart (see <<chart_selection>>) with the full zerotouch value set — content, terminal, wetty, novnc, cloud, ironrdp, stacked_terminals, second_terminal_tab, setup_automation, runtime_automation, satellite, route, and antora UI bundle — applies the rendered manifests, then waits up to `ocp4_workload_showroom_wait_retries` for the pod to become ready. If a container is stuck `waiting` in one of `ocp4_workload_showroom_fatal_container_reasons` (default: `CrashLoopBackOff`) for `ocp4_workload_showroom_fatal_container_restart_threshold` (default: `3`) or more restarts, it fails fast instead of waiting out the full retry budget. `terminal.terminals` and `wetty.sshOtherHosts`/`wetty.terminals` are built from the AgnosticD `instances`/`containers` inventory facts (any host/container with a `consoles` or `terminals` key becomes an extra terminal sub-tab).
- `tasks/check-and-install-helm.yaml`: installs `helm` from `{{ ocp4_workload_showroom_tools_root_url }}/helm/{{ ocp4_workload_showroom_helm_version }}/helm-linux-amd64.tar.gz` (OpenShift's own client mirror) if it's not already present at `/usr/local/bin/helm` or `/usr/bin/helm`.
- `tasks/report-variables.yaml`: waits for the `Route` named `ocp4_workload_showroom_service_name`, then writes `lab_ui_url` and `showroom_primary_view_url` (both set to the same URL) to `user_info`.
- `tasks/prepare_variables_destroy.yaml`: a leaner, defensive variant of `prepare-variables.yaml` used only by `remove_workload.yml`. Resolves `_showroom_user_data`/`_user_count` with `failed_when: false` (warning if the lookup returns nothing) — skips the `guid`/content-repo assertion and the Ingress-domain lookup, neither of which destroy needs.
- `tasks/remove_workload.yml`: if `ocp4_workload_showroom_deployment_type` was `argocd`, removes the matching `Application`/`ApplicationSet`. Always attempts to delete the `Project` for each namespace, with `failed_when: false` — on CNV sandboxes the namespace is the shared sandbox project the automation SA doesn't own, so this delete is expected to fail harmlessly (actual teardown happens at the infra/cloud-provider level). After each delete attempt, waits (up to 5 minutes, `failed_when: false`) for the `Project` to actually disappear, to avoid racing a fast guid-reuse re-provision against a still-`Terminating` namespace.

[#auth]
== Remote Cluster / Authentication

There are two independent, stackable authentication mechanisms. Understanding both avoids confusing failures:

[cols="1,1,3",options="header"]
|===
|Variables |Precedence |Behavior

|`showroom_openshift_api_url`, `showroom_openshift_api_token`, `showroom_openshift_api_ca_cert`
|Highest (if all three set)
|`pre_workload.yml` writes them into a temporary kubeconfig file (`_showroom_kubeconfig`), which every `kubernetes.core.*` task then uses via the `kubeconfig:` argument. Note these do **not** use the `ocp4_workload_showroom_` prefix.

|`ocp4_workload_showroom_openshift_api_url`, `ocp4_workload_showroom_openshift_api_token`
|Used when `_showroom_kubeconfig` is not set
|Passed as `host:`/`api_key:` directly on every task (same convention as the sibling `ocp4_workload_showroom` role, so callers already setting those vars for that role work here unchanged).

|(neither set)
|Fallback
|Tasks fall back to ambient `module_defaults`/environment (`group/k8s`, `K8S_AUTH_HOST`/`K8S_AUTH_API_KEY`) provided by the calling play. This is the pattern used by the original v1 CNV sandbox deployment (`module_defaults: group/k8s: {host, api_key}` set on the play that includes this role).
|===

[NOTE]
====
The `argocd` templates (`templates/application.yaml.j2`, `templates/applicationset.yaml.j2`) currently render a **reduced** value set compared to the `helm` path: they cover `terminal`, `wetty`, `content`, and `cloud`, but do **not** set `novnc`, `ironrdp`, `satellite`, `stacked_terminals`, `second_terminal_tab`, `setup_automation`/`runtime_automation`, `route.hostSuffix`/`omitHost`, or the Antora UI bundle override. If you need any of those, use `helm` deployment instead.
====

[NOTE]
====
This role's rendered `release_values` schema (`cloud`, `ironrdp`, `satellite`, split `setup_automation`/`runtime_automation`, `stacked_terminals`, `second_terminal_tab`, `route.hostSuffix`/`omitHost`, `antora.uiBundleUrl`, etc.) matches the `zerotouch` chart in https://github.com/rhpds/showroom-deployer[showroom-deployer], **not** the `showroom-single-pod` chart used by the sibling `ocp4_workload_showroom` role — those two charts diverged and no longer share the same `values.yaml` shape. If you override `ocp4_workload_showroom_deployer_chart_name`/`_version`, verify the target chart's `values.yaml` actually implements every feature you're relying on — Helm silently ignores unknown values, so an incompatible chart will not error, it will just no-op the feature (e.g. `ocp4_workload_showroom_ironrdp_enable: true` doing nothing).

== Multi-User

Multi-user mode is automatic: if `_showroom_user_data` (loaded from `user_data`) has a `users` map, the role loops once per user in `workload.yml`, `report-variables.yaml`, and `remove_workload.yml`, deploying one namespace/pod/route per user (`ocp4_workload_showroom_namespace-<user>`). Each user's `content.user_data` is that user's entry from `users` merged with `showroom_vars` and helper keys (`guid`, `user`).

== Examples

=== Minimal Single-User Deployment

[source,yaml]
----
guid: "abc123"
ocp4_workload_showroom_content_git_repo: "https://github.com/myorg/my-lab-content.git"
ocp4_workload_showroom_content_git_repo_ref: main
----

Include the role in your `env_type`'s infra workloads:

[source,yaml]
----
infra_workloads:
[ ... all your other infra roles ... ]
- agnosticd.showroom.zerotouch_showroom   # last
----

=== Shared / CNV Sandbox Cluster (ambient auth)

This is the pattern this role was ported from — no explicit `ocp4_workload_showroom_openshift_api_url`/`_token`, relying on `module_defaults` set by the calling play (see <<auth>>):

[source,yaml]
----
- name: Showroom deployer
  hosts: localhost
  module_defaults:
    group/k8s:
      host: "{{ sandbox_openshift_api_url }}"
      api_key: "{{ sandbox_openshift_api_key }}"
      validate_certs: false
  tasks:
    - name: Deploy Showroom as pods in the sandbox namespace
      include_role:
        name: agnosticd.showroom.zerotouch_showroom
      vars:
        ocp4_workload_showroom_namespace: "{{ sandbox_openshift_namespace }}"
        ocp4_workload_showroom_use_sandbox_domain: true
----

[#bastion_example]
=== Wetty Terminal with Auto-SSH to Bastion

`ocp4_workload_showroom_terminal_type: wetty` and `ocp4_workload_showroom_wetty_ssh_bastion_login: true` are already the defaults, so all you need to provide is the bastion connection data in `user_data` before this role runs:

[source,yaml]
----
- name: Provide bastion connection data
  agnosticd.core.agnosticd_user_info:
    data:
      bastion_public_hostname: "bastion.{{ guid }}.{{ cluster_dns_zone }}"
      bastion_ssh_user_name: "{{ remote_user }}"
      bastion_ssh_password: "{{ generated_password }}"
----

To use the `showroom` containerized terminal instead, override the type explicitly:

[source,yaml]
----
ocp4_workload_showroom_terminal_type: showroom
----

=== Multi-User Workshop Deployment

Ensure `user_data` contains a `users` map:

[source,yaml]
----
users:
  user1:
    bastion_public_hostname: "bastion1.example.com"
  user2:
    bastion_public_hostname: "bastion2.example.com"
----

The role deploys one namespace/pod/route per user, e.g. `showroom-<guid>-user1` and `showroom-<guid>-user2`.

=== ArgoCD Deployment

Requires OpenShift GitOps already deployed with cluster-admin RBAC for the system ArgoCD:

[source,yaml]
----
ocp4_workload_showroom_deployment_type: argocd
----

Remember the ArgoCD templates render a reduced value set — see the note under <<deployment_types>>.

[#gotchas]
== Known Gotchas

* The `argocd` deployment type renders fewer chart values than `helm` — see the note under <<deployment_types>>.
* The default chart name/version (`zerotouch` chart, `1.10.2`) and several other defaults (terminal type, wetty auto-SSH, zero-touch bundle/UI, Antora UI bundle, cloud image, `use_sandbox_domain`) are pinned to match real ZT RHEL BU production usage — see <<chart_note>> and the per-section tables above for what changed from the plain upstream/v1 defaults.
* `ocp4_workload_showroom_openshift_api_url`/`_token` and `showroom_openshift_api_url`/`_token`/`_ca_cert` are similarly named but distinct mechanisms — see <<auth>>.
